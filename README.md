# NetDoctor: diagnose network problems from packet captures

> Cybersecurity Hackathon, IIITDM Kancheepuram, Network Track.
> Drop in a `.pcap` / `.pcapng`, get a plain-language answer to **"is my network broken, or is it under attack?"**

## The problem
Small offices, labs and campus departments have no network engineer. When the network is slow or strange, the only
way to find out why is to read a packet capture line by line, which needs deep protocol knowledge. Worse, an outage
and an attack both look like "the network is broken", so people reboot the router while the real problem continues.

## The solution
NetDoctor reads a capture, finds faults **and** attacks, separates the two, and for every finding gives:
what happened (plain language), the likely cause, a suggested fix, a confidence score, and the **exact packets** as evidence.
Output is a terminal report, JSON, or a self-contained HTML report with a timeline. A small local web dashboard is included.

### What it detects
| Faults | Attacks |
|---|---|
| TCP retransmissions (packet loss) | Port scans and host sweeps |
| Unreachable servers (SYN never answered) | ARP spoofing / man-in-the-middle |
| TCP resets (refused vs aborted) | DNS hijacking (forged or conflicting answers) |
| DNS failures (NXDOMAIN/SERVFAIL), DNS timeouts, slow DNS | Rogue DHCP servers |
| Duplicate IP addresses / ARP conflicts | |
| MTU mismatch (ICMP "fragmentation needed", large-segment black holes) | |
| Slow connection setup (unusual delays) | |

### How it tells an outage from an attack (and keeps false alarms low)
* Attack rules need behaviour a broken network does not produce: **unsolicited** ARP replies, **port fan-out**
  with unfinished handshakes, **conflicting** DNS answers for one question, a **second DHCP server with different gateway/DNS**.
* A busy browser opening many connections to port 443 is *not* a scan; a scan must hit many distinct ports/hosts in
  10 s and leave most handshakes incomplete.
* Two devices answering ARP only when asked = **duplicate IP (fault)**; one device flooding replies nobody asked for = **ARP spoofing (attack)**.
* A second DHCP server handing out the *same* gateway/DNS is flagged as a **misconfiguration**, not an attack.
* Scan sources are excluded from fault rules (their resets are not "a broken service").
* If a fault involves hosts named in an attack, the report says it is probably a **side effect** and to deal with the attack first.
* All thresholds are constants at the top of `netdoctor/detectors.py`.

## Setup (about one minute)
```bash
git clone <this repo> && cd netdoctor
python3 --version        # 3.9+
# Core tool needs NOTHING to install (standard library only).
python -m netdoctor samples/08_mixed_incident.pcap                      # terminal report
python -m netdoctor samples/08_mixed_incident.pcap --format html -o report.html
python -m netdoctor samples/03_arp_spoofing.pcap --format json
# Optional web dashboard
pip install -r requirements.txt && python -m netdoctor --serve          # http://127.0.0.1:5000
# Tests (includes fuzzing and web-upload checks)
python -m unittest discover -s tests
```
Exit code: `0` no attack, `1` attack found, `2` unreadable file (handy for scripts).

### Sample captures (`samples/`, synthetic, generated by `tools/make_samples.py`)
`01_normal` (clean, must stay silent) · `02_outage_faults` (faults only) · `03_arp_spoofing` · `04_port_scan` ·
`05_dns_hijack` · `06_rogue_dhcp` · `07_duplicate_ip` · `08_mixed_incident` (faults + attacks together) · `malformed` (corrupt file).
They contain no real traffic. You can also try your own captures (only networks you own or have permission to capture).

## Security of the tool itself
* **Own parser, hostile-input safe:** every read is bounds-checked; DNS name compression loops are capped; corrupt
  or truncated files produce a warning, never a crash. Limits: 256 MB file, 500k packets, 256 KB per record.
* **Fuzz-tested:** the test suite randomly corrupts and truncates captures; no input may raise anything except a clean `CaptureError`.
* **Output is escaped:** DNS names in a capture are attacker-controlled, so every string in the HTML report is HTML-escaped, and the report ships with a strict Content-Security-Policy.
* **Web dashboard:** binds to `127.0.0.1` only, 50 MB upload limit, upload stored in a temp file under a random name (never the client filename) and deleted immediately, `nosniff` + CSP headers.
* The tool never opens network connections and never captures live traffic. No credentials, keys or secrets exist anywhere in the repo.
* One failing detector cannot break the report (isolated and reported as a warning).

## Architecture
```
capture file -> pcap.py (pcap + pcapng reader, limits)
             -> dissect.py (Ethernet/VLAN/ARP/IPv4/TCP/UDP/ICMP/DNS/DHCP)
             -> detectors.py (all detection + diagnosis logic)
             -> analyze.py (run rules, correlate faults with attacks, verdict)
             -> report.py (text | JSON | HTML timeline)      web.py (Flask dashboard)
```

## Third-party libraries (full list)
* **None for the analysis engine**: the capture reader, dissectors and all detection logic are original, pure Python standard library.
* **Flask** (BSD-3): only for the optional `--serve` dashboard.
* We deliberately do not use Scapy, PyShark, Wireshark or tshark.

## Limitations (honest list)
IPv4 only (IPv6 is skipped), no TCP stream reassembly, no TLS inspection, cannot decode Wi-Fi/802.11 frames, only Ethernet
and Linux-cooked link types. Heuristics are tuned on synthetic captures; on real networks, thresholds may need adjusting.
A rogue-DHCP vs misconfiguration call and ARP spoofing vs duplicate IP are strong signals, not proof.

## Ideas for next steps
IPv6/NDP, TCP RTT and window analysis, SYN-flood and DNS-tunnelling detection, live capture mode, per-network baselines to cut false positives further.

*Use responsibly: test only on samples or networks you own or are authorised to analyse.*
